# LumaFrame — Multi-agent orchestration

How work is split across simultaneous coding agents, and how it comes back.

Main model owns: the task definitions, the quality gate, the merge order, and the final
verdict. Agents own: the files assigned to them, and nothing else.

---

## 1. The hard constraint that shapes everything

**There is no Mac and no Xcode on this machine, and no Android SDK.** An agent cannot
compile Swift, cannot run `xcodebuild`, and cannot run the iOS unit tests locally. It can
only edit text and run Node.

What an agent *can* run locally:

```bash
node scripts/generate-pbxproj.mjs --check   # project file matches disk
node scripts/validate-pbxproj.mjs           # all object IDs valid, all paths resolve
node --check <file>                          # nothing; Swift/Kotlin are not checkable here
```

So **the quality gate is CI, not the agent's machine.** That is exactly why each agent gets
its own worktree: a branch that fails to compile costs one CI run and a rejected PR, never
a broken `main` and never a conflict in someone else's working tree.

**Consequence to accept openly:** the first wave will produce branches that fail to build.
That is expected. The gate catches it. Do not let an agent claim success by inspection.

---

## 2. Worktree protocol

One worktree per agent, branched from the agreed base commit.

```bash
# created once, from a clean base
git worktree add ../lf-a1 -b agent/a1-lut-colour      main
git worktree add ../lf-a2 -b agent/a2-manual-exposure main
git worktree add ../lf-a3 -b agent/a3-ui-consolidation main
git worktree add ../lf-a4 -b agent/a4-looks-storage   main
git worktree add ../lf-a5 -b agent/a5-diagnostics     main
```

Rules:

1. **Never work in the main working tree.** It holds the plan documents.
2. **Never `git push --force`, never amend a commit that has been pushed.** A force-push
   destroys the review diff.
3. **One commit per task file is ideal**, with a message naming the task id. Review is
   easier with `a1: ...` in the log.
4. **Never touch a file you do not own.** If you need one, stop and report. A blocked
   agent is a good outcome; two agents silently editing one file is a bad one.
5. **Do not merge to `main` yourself.** Push the branch, open a PR, and the main model
   merges after review.

---

## 3. The `project.pbxproj` is derived state — this resolves most conflicts

The Xcode project uses explicit file references and is generated by
`scripts/generate-pbxproj.mjs`, which walks the sources and assigns deterministic object
IDs from a hash of each path.

**Any agent that renames, moves or deletes a source file will touch `project.pbxproj`,
and two agents doing so will conflict on it. That conflict is expected and is not a
problem**, because the file is not a source of truth — it is a projection of the directory
listing.

Merge protocol:

1. When `project.pbxproj` conflicts, **take either side and do not hand-merge it.**
2. After all agent branches are merged, run, from the main working tree:
   ```bash
   node scripts/generate-pbxproj.mjs
   node scripts/validate-pbxproj.mjs
   ```
3. Commit the result as `chore: regenerate project file after wave merge`.

Every agent must still run the generator before pushing, so that a branch is independently
valid and its CI run is meaningful. But the final regeneration is the authority.

## 4. File ownership

Ownership is disjoint by construction. Two agents must never own the same file.

| Agent | Task | Owns |
| --- | --- | --- |
| **A1** | LUT colour correctness (defect 1) | `Processing/{CubeLUT,CubeLUTError,CubeLUTParser,ColorSpace,LUTProcessor,ProcessingPipeline}.swift`, `Tests/{LUTProcessorTests,ProcessingPipelineTests}.swift` |
| **A2** | Manual exposure, composite device, photo quality (defects 2 + 3) | `Camera/{ProCapabilities,CaptureSessionController,PhotoCaptureController,CameraCapabilities,CameraViewModel}.swift`, `Tests/CameraStep1Tests.swift` |
| **A3** | Camera view consolidation | `Camera/{ProDial,ProChipBar,TonePanel,LooksChipBar,PreviewView,ProcessedPreviewView,PreviewMeter,ProcessedPreview}.swift` |
| **A4** | Looks + Storage consolidation | `Looks/*.swift`, `Storage/*.swift` |
| **A5** | Diagnostics consolidation | `Support/{RuntimeCapabilities,ReportFormat,DeveloperPanel,MemoryProbe}.swift`, `Camera/CameraRelease.swift` |

Explicitly **not owned by anyone in this wave**, on purpose:

- `Camera/CameraScreen.swift` — hosts the views A3 moves. It should not need editing
  because moving a declaration does not change its call sites. If A3 finds it must edit
  it, that is a finding, not a task.
- `App/*`, `DesignSystem/Theme.swift`, `Support/{AppLog,Haptics,LumaFrameLogFile,MemoryProbe→A5,LumaFrameSafety*}`, `ML/SubjectSegmentation.swift`, `Processing/{ProcessingSettings,SubjectMask,ToneCurve}.swift`, `Tests/CubeLUTParserTests.swift`.
- `CameraViewModel.swift` consolidation — it is 37 KB and wants splitting, but A2 needs it
  to plumb manual state. **Consolidation of that file is wave 2, deliberately.**

### The one cross-agent risk

A1 changes API in `Processing/`; A2, A3 and A4 consume it. Consolidation agents (A3, A4,
A5) are therefore bound by a hard rule:

> **Moves only.** Do not change a type's name, signature, access level or behaviour. Do not
> fix anything you notice. If a move appears to require a signature change, **stop and
> report it** rather than making it.

A1 is bound by the mirror rule:

> Do not rename or change the signature of any `Processing/` type used outside
> `Processing/`. If the colour-management fix appears to require it, stop and report.

## 5. Quality gate

An agent's work passes when **all** of the following hold. The main model checks them in
order; the first failure sends the branch back.

**Mechanical**

1. `node scripts/generate-pbxproj.mjs --check` and `node scripts/validate-pbxproj.mjs` pass.
2. CI green: `Unit tests` and `Build unsigned IPA` on the branch.
3. `git diff -M --stat main...` shows what it should: consolidation agents show renames and
   near-zero line churn; defect agents show real deltas.
4. No file outside the ownership table is modified.
5. No force-push, no amend of pushed history, no changes to `.github/workflows/`,
   `project.pbxproj` beyond the generator's own output, or `docs/`.

**Consolidation agents (A3, A4, A5) only**

6. `git diff -M main...` shows every hunk as a pure relocation. Any hunk that changes a
   line of code is a rejection — that is a behaviour change wearing a move's clothes.
7. File count decreases. Net line count should fall only by deleted duplicate comments.

**Defect agents (A1, A2) only**

8. Every new or changed AVFoundation/Core Image API is justified with a citation in the
   commit message.
9. No model-name, marketing-name or `hw.machine` branching anywhere. `hw.machine` may be
   read for display only, never in a conditional.
10. Tests fail before the change and pass after. A defect fix without a failing test is
    not a fix, it is a hope.
11. No new features, no new dependencies, no new screens.
12. A log line is added wherever a capability is probed, a capture setting is applied, or
    a decision is taken that a reader on a device could not otherwise explain.

**All agents**

13. No unexplained `fatalError`, no `try!`, no force-unwrap on anything from AVFoundation,
    no unbounded allocation in a loop.
14. Comments explain *why*, not *what*. The existing code sets a high bar here; match it.

## 6. Merge order

Not arbitrary. A1 and A2 change API; A3, A4, A5 do not.

1. **A1** — `Processing/` colour management.
2. **A2** — Camera manual exposure. Depends on nothing from A1, but lands second so its
   CI run overlaps A1's and problems surface in parallel.
3. **A3**, **A4**, **A5** — consolidation, in any order among themselves. Each is a pure
   relocation, so they merge cleanly against each other.
4. Regenerate `project.pbxproj`, validate, commit.
5. Full CI on `main`. Only then is the wave done.

A1 and A2 are the two that will take longest and are the two worth starting first.

---

## 7. What this wave is not

- **Not verification.** Nothing here runs on a device. `docs/IOS_PLAN.md` section 5 says
  the critical path is running the build; that is still true and is not delegated to an
  agent, because no agent here can do it.
- **Not new features.** Explicitly out of scope. The app has five unverified steps; adding
  a sixth is how it got here.
- **Not a rewrite.** Consolidation reduces the file count and makes each file cohesive.
  It is explicitly **not** "break the big files up" — the target is fewer, larger files.
